## 2. 要先决定的三件事

1. **U6 需要新题型 `pick`（读报错选择题）**，候选分支 `release/v1-candidate` 里没有这个题型的渲染和判分。所以 U6 **不是纯内容合入**：要连同题型代码、样式和测试一起带进去，并在 390×450 和 390×844 上各验一次。U7 只用现有三种题型，是纯内容。
2. **base 不对**：#51、#48 的 base 是 `dsh/login-sync-hardening-3`，和候选分叉（#51 相对候选有 13 个独有提交，其中含登录同步方面的旧改动）。接入前要在候选之上新开分支，只摘 U6 / U7 的内容和 `pick` 相关改动，**不能整条合并**，否则会把旧的登录同步代码带回来。
3. **第一版不加**：按产品决定，第一版继续锁定 U1–U5；U6、U7 在第一版验收和发布之后另开线，逐个验收。

## 3. 审校清单（每关逐项勾）

- **学习目标**：这一关只教一个新概念吗？有没有同时引入两个？
- **误区**：每道 predict / pick 的错误选项是否对准一个具体误区，并各有一句 `why`？（参照 `docs/44` 的“值得沿用的做法”。）
- **真实性**：`verify:content` 全部通过（见上表）；pick 的 `trace` 是真实 Python 报错原文，`checks` 里 type / line / msg 与真实运行一致。
- **读法**：prompt 是否让没学过编程的人读得懂？术语第一次出现有没有一句话解释（如 Traceback、TypeError、KeyError）？
- **干扰项质量**：有没有“蒙对也不知道为什么”的选项（如数值恰好等于正确答案）？
- **手机端**：每种题型在 390×450 下选项可达、「检查」可点、反馈后「继续」可点；长代码行不横向溢出（U7 已加 28 格行宽检查）。
- **PR 描述**：写明本关打的误区、验证次数、浏览器通过情况。
