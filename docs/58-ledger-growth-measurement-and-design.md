## 1. 测量方法
- 脚本：`scripts/measure-ledger-growth.mjs`（PR #78 `11d33b8`，`node scripts/measure-ledger-growth.mjs [--json]`）。
- 纯内存假 localStorage；不碰任何真实用户存档；`_auto.on=false`，压缩关闭。
- 模拟用户：每次打开 = 一个新页面 id；**最坏情形：每次打开都保存一次**（真实用户不一定每次都写）；每天第一次打开完成一关（前 34 关首次，之后重复刷）；红心每次打开变化一次（让 meta 变化）。
- **体积单位（三种，不能直接互换）**：①本表的“字符数”= 键名 + 值的 **UTF-16 代码单元数**（JS 的 `.length`，脚本里的数）；②“估算字节”：多数浏览器内部按 UTF-16 存储，粗算约为代码单元数 ×2，但各浏览器实现不同，这只是估算，没有实测；③“浏览器报告的 Origin 配额”：`navigator.storage.estimate()` 给的是整个站点（IndexedDB、缓存、localStorage 等）的用量与配额，**不等于 localStorage 自己的上限**，本文没有测，真机上要用诊断页读出来再对照。localStorage 的上限在各浏览器 / 版本之间不同（常见说法约 5M 字符或 5MB，没有逐个实测），所以下面任何“写满”都只是对小配额的模拟。
- **耗时是 Node 里 JS 解析+合并的开发者测量，不含真机逐键读取 localStorage 的开销；它不是真机或 CI 性能证据，也不推断真机快慢**；这里只用来看随键数增长的趋势。

- 高频刷新 365 天需模拟 7300 个页面，保存时每次完整合并是 O(n²)，模拟太慢，只量到 90 天；之后按每键平均字符数外推。
- **平均每个账本键约 306 字符**（含键名）。早先 Fable 审计估算约 720 字符/键，偏大；以这次模拟为准，但真实用户的账本（有更多完成关卡、firstXp、doneOn）会更大，上限需要用真实环境的“复制诊断”里的“本机存储：N 个键，约 X KB”核对。
- **写满行为**（小配额 300,000 字符快速写满）：第 51 天开始保存被拒绝（7000 次拒绝），保存返回 false（页面会提示“无法保存进度”）；**已写入的 34 关、XP 2500 仍可正常读取**；写满之后新做的进度只在页面内存里，关页即丢。
- **（已撤掉年数换算）**（配额因浏览器而异，真实账本更大）。外推到 5,000,000 字符：可容纳约 16,339 个账本键；每天 3 次约 14.9 年、每天 20 次约 2.2 年、每天 3 次×2 标签约 7.5 年写满（均为“每次打开都保存”的最坏情形）。

## 3. B 要分别交代的两件事（不混称“压缩完成”）
**读取性能**（每次打开都要扫描全部账本）：
- 键数线性增长，完整读取耗时在模拟里也近似线性；模拟下 2190 个键约 6ms。真机逐键读取耗时**未实测**（不作数量级推断），需要在隔离 iPhone 上用诊断页的键数做对照后再下结论。
- 保存时也要做一次完整合并（防覆盖别页），所以保存耗时同样随键数增长。

**存储容量**（localStorage 总字符数）：
- 在“不删历史数据”约束下，容量只增不减；任何“汇总副本”都是在原键之外**多一份**，不会降低总占用。
- 碰到上限的时间取决于浏览器实际的 localStorage 上限、真实条目大小和打开频率，当前没有可靠数据，**不给年数**。

## 4. 设计对照（不删除历史数据）
| 方案 | 能改善 | 不能改善 | 风险/说明 |
|---|---|---|---|
| A. 汇总索引键（只读缓存）：记下“已知账本键列表+各自指纹”，打开时先读汇总，再只读新增/变化的键 | 读取次数（大量键的 getItem 调用）；完整快照仍可校验 | 总容量（反而多一个键） | 只读缓存，丢了可重建；不删原键；索引本身是共享可变记录，要用“按设备/按页”写法避免覆盖，或视为可丢的缓存 |
| B. 减少未来新增账本量：页面没有进度/meta 变化时不写账本键 | 键数增长（可能砍掉大部分“打开即保存”产生的键） | 已有历史键 | 需确认当前哪些保存是必须的（红心恢复、偏好）；改动小、可逐步灰度；不涉及迁移 |
| C. 缩小每个账本条目：省略空字段、缩短重复的 prefs/meta | 每键字符数（约 306 → 估计 150–200） | 键数 | 读取兼容旧格式即可；不迁移旧键；节省有限 |
| D. 把 meta（红心、偏好）放进一个“最近者胜”的小共享键，不再每页账本重复携带 | 每键体积、合并成本 | 键数 | meta 已是 `meta.t` 最新者胜，语义不变；但这是共享可变记录，需要评审并发（丢最后一次偏好可接受，丢进度不可接受）；仅限 meta，不含进度 |
| E. 带锁的压缩（Web Locks，保存与压缩共用同一把锁）后允许删除 | 容量与读取两者 | — | **当前禁止**：产品官要求不删除；仅记录为远期，需先证明锁覆盖保存全路径，不支持 Web Locks 的浏览器（旧 Safari）不能做 |

在“不删除”约束下**仍无法解决**：已经写下的账本占用不会下降；高频用户最终仍会写满，只能延后（B/C/D 方案把每年增长降到原来的一部分），写满后依靠导出进度/进度码备份和“无法保存”的明确提示兜底。

## 7. 撤回说法（22:23）
撤回“localStorage 同步 API 让保存具备跨标签原子性”一类说法。同步 API 只保证单次 getItem / setItem 本身不被打断；“读 → 合并 → 写”这一串在不同标签之间**不是原子的**。v4 的安全性来自“每页只写自己的键 + 读时合并（并集/最大值/求和）+ 清除用新一代 epoch”，而不是同步代码的原子性。
