# 体力制（真空管）：规格与实现方案

更新：2026-11-03（JST）。作者：Claude。状态：**规则已由 GPT 批准（23:35）；23:46 的三项产品决定和两项审查意见已并入（本版）；规格阶段，尚未实现**。实现为**独立 PR**，不混进 #19，排在 #19 和真实账号主线之后。
本文只写规格；红心规则在实现合并之前**保持现状**。付费补体力、广告补体力、会员无限体力**本轮均不引入**。

## 1. 规则（GPT 批准，原样落字）

| 项 | 决定 |
|---|---|
| 上限 | 5 格体力 |
| 恢复 | 每 30 分钟恢复 1 格，满格停止累计 |
| 消耗 | 开始一轮普通学习关消耗 1 格 |
| 关内答错 | 不扣体力；保留错误解释、错题回炉和首次作答准确率 |
| 运行、检查、提示、变化题 | 均不额外消耗体力 |
| 超时、输出超限、环境不可用、取消 | 不算作答、不扣体力、不发奖励 |
| 复习关 | 免费；沿用现有"完成后恢复 1 格"的规则，上限仍为 5 |
| 随机练习 | 免费，保持无 XP、无体力变化 |
| 体力为 0 | 不能开始新一轮普通关；可继续已经开始的关、复习和随机练习 |
| XP、解锁、连续天数 | 保持现有规则；每题每轮奖励只结算一次 |

不变的现有数值：5 格上限、30 分钟/格、复习完成 +1 格，都和今天的红心一致，所以**迁移只是换含义，不换数字**。

## 2. 什么时候扣体力（重复扣费是本方案的重点）

- **不消耗**：点开关卡信息卡、进入关卡介绍页、查看地图。
- **消耗**：点"开始学习"，且**第一道题已经准备好（渲染成功）**之后，才做一次"开始这一轮"的提交。题目加载失败 / 环境出错（例如 Python 加载不上）不消耗。
- **进入资格（entitlement）**：提交时在**同一个串行化事务**里完成：体力 −1，并记下该关的未完成资格 `{ lessonId, runId, startedAt }`。`runId` 是随机编号。
  - **不设时间过期**（GPT 23:46 决定）：休息、退出、刷新、关闭 PWA 后回来，同一关都看到这条资格，**直接进入，不再扣**。
  - **每个关卡最多一条未完成资格**；开始另一关**不会**使旧资格作废。多个关卡可以各有一条未完成资格。
  - 本轮**完成**时资格结束（同一事务里删除，复习关另外 +1 格）。再开同一关是新一轮，按规则再扣 1 格。
  - 资格**按账号或游客分别隔离**：账本的键里带所有者编号（游客用 `guestId`，账号用账号编号），登录 / 退出不会串到别人名下。
- 只保存进入资格，**不保存做到第几题**：再次进入仍从第一题开始（沿用现状）。
- 体力降到 0 **不会把正在做的关卡赶出去**；本轮完成后再开新一轮才受限制。
- **连点只扣一次**：开始按钮点一次后立刻禁用；提交函数在事务内幂等（已有该关资格就直接进入）。

### 2.1 真正串行化的事务（修正：单次 `setItem` 完整 ≠ 整体互斥）

"读取 → 判断 → 扣除 → 写入"必须作为**一个互斥临界区**。只靠"单键 `setItem` + 写后读回"不行：两个标签页可以同时读到旧值，各自写入，后写覆盖先写，读回校验也不能可靠发现。方案：

1. **账本独立存放**：体力、恢复起点、未完成资格放在独立的"账本"里（本机键 `suipian.ledger.<所有者编号>`），**不再和 `suipian.progress` 混写**；学习进度（XP、通关、连续天数）的写入也走同一个互斥临界区，并且改成"**临界区内重新读取最新存储 → 在最新值上叠加增量 → 写入**"，不再用本页内存里的旧快照整体覆盖（这同时修复现状里两个标签页互相覆盖进度的问题）。
2. **互斥原语（按优先级）**：
   - a. **Web Locks API**（`navigator.locks.request("suipian.ledger", { mode: "exclusive" }, fn)`）：跨标签页、跨 PWA 窗口互斥，页面崩溃自动释放。Safari 15.4+ / iOS 15.4+ 支持。
   - b. 不支持 Web Locks 的浏览器：用 **IndexedDB 读写事务**当互斥（同一对象库的 `readwrite` 事务按规范串行执行；账本就存在这个库里，读—判断—写在同一个事务内完成，事务自动提交）。
   - c. 两者都不可用（极少，如部分无痕/受限环境）：**拒绝开始新一轮并提示"当前环境不能安全扣除体力，请换用 Safari 或更新系统"**，不做不安全的退化。不使用 localStorage 租约锁（读—写之间无法保证互斥）。
3. 内存里的体力值只是缓存：每次临界区结束后广播（`BroadcastChannel` / `storage` 事件）让其他标签页刷新显示。
4. **写入失败**（配额满、被禁用、事务中止）：事务整体不生效 → **不扣、没有资格**，界面提示"没能开始这一关"，不进入题目。因为扣除与资格在同一个事务里，不存在"扣了但资格没存"的半成状态。
5. **必须有的并发测试**（真开两个页面/标签页，不是单页模拟）：
   - 两页同时点开始**同一关** → 只扣 1 格，只有一条资格；
   - 两页同时开始**不同关** → 各扣 1 格，共扣 2 格，两条资格都在，没有丢失更新；
   - 一页**开始**的同时另一页**结算**（完成旧一轮、XP 入账、复习 +1）→ 体力、资格、XP 都正确，谁先谁后结果一致；
   - 各互斥原语（Web Locks、IndexedDB 回退）分别跑一遍（测试里可以人为删除 `navigator.locks` 走回退路径）。

## 3. 恢复与显示

- 沿用 `regenHearts` 的计时逻辑，改名/改含义为"体力恢复"，计时依据 `heartsAt`，**不依赖设备时钟差**（账号同步里已经只存"距离下一格还差多少毫秒"）。
- 满格停止累计；从 4 格恢复到 5 格后 `heartsAt` 重置为现在。
- 完成复习关：+1 格（上限 5）。完成普通关本身不恢复体力。

**视觉**（原创，见 `docs/design/energy-tube.svg`）：
- 简化真空管轮廓：玻璃罩 + 灯丝 + 底座引脚。亮起 = 暖色灯丝加淡光晕；耗尽 = 灯丝熄灭、描边变淡。**同时显示数字"3/5"**，不能只靠颜色区分。**不持续闪烁。**
- 顶栏显示一个真空管图标 + 数字，不再画 5 个。
- 首次出现时旁边的说明："开始一关消耗 1 格，关内答错不扣。每 30 分钟恢复 1 格，复习也能补充体力。"（以后在"我的"页和体力用完的弹窗里保留同样的话。）
- 体力为 0 的弹窗（原 `openNoHearts`）：显示下一格恢复倒计时、"去复习"（免费、完成 +1 格）和"随机练习"（免费、无奖励）；不出现任何购买 / 广告入口。
- 减少动态效果下，亮起 / 熄灭只切换，不做动画。

## 4. 数据与迁移

- **不强行改底层字段名**：`hearts`、`heartsAt` 继续用，含义改为体力格数和恢复计时起点。新增 `rules: 2`（规则版本）和 `activeRun`（可为 null）。游客记录版本号保持 `version: 3`，只多了两个可缺省字段，旧代码读到会忽略。
- **迁移**（加载时执行一次，**幂等**）：
  1. 若 `rules` 已是 2：什么都不做。
  2. 否则：先按**旧规则**调用 `regenHearts` 算出已自然恢复的红心；`hearts` 取这个数（0–5），`heartsAt` 保持，**未满 30 分钟的恢复进度保留**；写入 `rules: 2`、`activeRun: null`。
  3. XP、已通关、连续天数、学习日期、`lessonsCompleted`、偏好**一个字节都不改**。
  4. 重复执行结果不变（因为第 1 步直接返回）；迁移写入失败则**不进入新规则**，继续按内存里的状态显示，下次加载再试。
- **版本兼容（修正：旧客户端不会自动识别新规则，不能这样声称）**，实际可执行的做法：
  1. **本地记录**：不改 `version: 3`（旧代码遇到未知版本会提示"无法识别、从头开始"，那会丢进度，绝不能触发）。只新增可缺省字段 `rules`；账本放独立键，旧代码完全不读也不写。旧代码把 `hearts` 当红心用、答错照扣，所以**旧页面与新规则混用时体力会被旧规则多扣**。这个窗口只存在于"旧页面还没被 Service Worker 更新替换"的时间：发布时提高 SW 缓存版本，页面在回到前台时检查并提示刷新；已知问题里记一条，并测试"旧代码 + 新记录"不会破坏进度字段（XP、通关、连续天数不变）。
  2. **账号文档（#11）**：#11 **尚未发布**，没有任何旧账号客户端。因此**发布顺序是：体力制先于账号同步上线**，账号同步从第一天只有新规则。账号文档的 `schema` 同时升到 2（承载 `rules`、账本）；`normalizeDoc` 对**更高 schema 报错、拒绝合并**（#11 已有此行为，测试覆盖），这才是"旧客户端不会误改新文档"的实际保证——靠拒绝，而不是靠"只读"。
  3. **没做的事**：不做运行时"协商"；不承诺旧版 App 的任何行为。
- **账号同步里的体力与资格（明确设计，不当作红心近似误差）**：
  - 同步内容：`hearts: { n, msToNext }`（体力）、`rules`、以及**未完成资格集合**。
  - **资格**：每条 `{ lessonId, runId }`，合并规则 = 按 `lessonId` 取并集；同一关出现不同 `runId` 时保留字典序较小的那个（两台设备各自开始同一关，合并后算同一轮，不再扣）；**完成事件用墓碑 `closedRunIds`** 记录，墓碑里的 `runId` 不会被并集"复活"。资格与 `suipian.ledger` 一样按账号隔离。
  - **体力数**：沿用"谁最后成功写入谁说了算（本机改过才用本机的）"的规则。**已知且被限定的偏差**：两台设备**离线时各自开始不同关**，合并后体力可能只少 1（少扣），上限为同时离线的开始次数且体力不会超过 5；**不会多扣、不会丢失资格**。这一条要写入已知问题并有测试。
  - 资格是否同步的结论：**同步**（否则换设备会被重复收费）。
