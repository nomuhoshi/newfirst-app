## 0. 给新产品官的第一段话

你是「碎片编程」的产品官（PO）。你的工作：拆任务、排优先级、审查交付、记录决定。你不写代码，不碰数据库；你给程序员 Claude 下指令，程序员把结果和证据回给你。**只有老大能批准**：合并 main、正式部署、正式数据库写入、删除、花钱、改锁定规则。

读完本文后，你的第一条消息建议是：确认已接手，复述当前最高优先级（§6），并向老大要第 1 项授权（§6 的 P1）。

## 4. Fable 的指挥：全 app 分析检查和完善顺序

> 来源：2026-11-10（东京）程序员聊天里，老大让程序员切到 **Claude Fable 模型**，按“检查这个网站现在的完成度，看看是否有漏洞 / 冗余的地方；制定一个网站完善顺序图”做了一次全 app 只读检查（东京 17:58 交付，没有改任何代码）。下面是它的结论和指挥要点，以及到 2026-11-11 15:4x 的执行情况。之后各项工作都按这张顺序图推进。

### 4.1 Fable 的核心结论

**最大的问题不是功能没做完，而是做完的东西几乎都没上线。** 当时正式站（main）只有 U1–U2、没有账号；发布候选比 main 领先 172 个提交。卡住上线的只有两件事：iPhone 真机验收和发信域名，都在老大手上。

| 方面 | Fable 的判断 |
|---|---|
| 数据库权限 | 没问题：表只读，写入只走 3 个函数，函数里一律用 `auth.uid()`，单个账号进度限 64 KB，源码里只有公开密钥 |
| 漏洞 / 风险 | ① 没有 CSP（页面被注入脚本时，存在 localStorage 的登录凭证可被读走）；② 没有隐私说明页（账号功能收集邮箱）；③ 正式环境没配自有 SMTP，上线后验证码可能发不出；④ GitHub Actions 只固定到大版本（`checkout@v4`），没固定到提交；⑤ 云端只校验进度大小、不校验格式（只影响用户自己那一行，优先级低）；⑥ 正式库的 schema 没核对过 |
| 冗余 | 远端 183 条分支只有 4 条进了 main；30 个开放 PR，其中 #11、#19–#25、#38、#40–#42、#44 已被候选包含；U6、U7 各有两条内容线；预览仓库 177 MB、15 个目录、每个各带一份 Pyodide；docs 24–37 号是登录加固过程记录（28 号重复、20 号缺）；AGENTS.md 过时；三个预览工作流功能重叠 |
| 要老大决定 | 发布候选主干选哪条；发信域名；清理（删分支、删预览目录）是否现在做 |
