# 56 iPhone 两项失败的专项诊断（Fable，2026-11-12 01:1x）

诊断：Fable（受产品官 5 号指定）；程序员核对后整理。基于正式版 main `f7c5f22` 的同源构建，在本机 Chromium 实测（本机没有 WebKit；真 Safari 只有老大截图作证）。应用代码**未改**；诊断测试在分支 `diag/ios-feedback-progress` `753cf59`（只加 2 个测试文件，未开 PR、未合并、未部署）。

## 1. 反馈遮挡（H3）—— 根因确认，**D6 回归**

**根因**：D6 给「继续」加了 `position: sticky`，sticky 的 `bottom` 和 `.feedbar` 的 `padding-bottom` 留了**同一份**底部空白，两份叠加，把按钮往上顶。sticky 的参照范围是滚动容器去掉 padding 后的区域；iOS 浏览器下 padding 已留 80px，`bottom: 80px` 又要求再离 80px（`src/game.css` 第 230–231 行与第 155、227 行）。
- 短反馈（答对）：按钮顶到内容顶部，只剩自己的 10px 上边距 → 盖住「答对了」标题（老大截图）。
- 长反馈（答错）：按钮整整上移 80px，盖住解释和正确答案。
- 主屏幕 App：padding 14px + 安全区 34px，`bottom` 也是 34px → 上移 34px，同样会盖。

**证据**
- 老大截图（1206×2622，3x → 402×874）：反馈区顶约 598.7，「继续」顶约 622.7，差 24px = padding-top 14 + margin-top 10，与机制一致。
- 本机复现（iPhone UA 使 `ios-browser` 生效，402×659 ≈ 截图可视区）：

| 场景 | 反馈区 | 标题 | 「继续」 | 结果 |
|---|---|---|---|---|
| U1L1 填空答对（同截图） | 483–671 | 497–529 | 507–559 | 盖住标题 22px |
| U1L1 排序答错 | 303–659 | 317–349 | 447–499 | 盖住「正确答案」34px |
| 主屏幕 App（安全区 34px，402×874）填空答对 | 684–840 | 698–730 | 708–760 | 盖住标题 22px |

- 版本对比（`tests/feedback-ios-sticky.test.mjs`：选输出 / 填空 / 排序 × 答对 / 答错，U1L1 + U3L8，Safari 与主屏幕 App 两种）：**D6（=正式版）6 过 114 败**；D5 122 过 1 败（那 1 项是 D6 本来要修的矮屏挤出）；**D6 + 候选修复 120 过 0 败**。
- 截图：复现 [答对](evidence/2026-11-12-fable-diag/chromium-safari-659-right.png)（与老大原图形态一致）、[答错](evidence/2026-11-12-fable-diag/chromium-safari-659-wrong.png)；修复后 [答对](evidence/2026-11-12-fable-diag/chromium-safari-659-right-fix.png)、[答错](evidence/2026-11-12-fable-diag/chromium-safari-659-wrong-fix.png)、[主屏幕 App](evidence/2026-11-12-fable-diag/chromium-pwa-874-right-fix.png)。

**为什么 D6 验收没抓到**：D6 的自动化和桌面响应式复核都没带 iPhone UA 和安全区；那种条件下 padding 只有 14px、`bottom` 为 0，两份留白不叠加。

**最小修复**（只改 `src/game.css`）：
```css
.feedbar > [data-continue] { position: sticky; bottom: 0; }
/* 删除：.ios-browser .feedbar > [data-continue] { bottom: 80px; } */
```
留白继续由 `.feedbar` 的 padding 负责。保留 D6 的“长反馈内部滚动”。把 `tests/feedback-ios-sticky.test.mjs` 接进 CI。

**另一现象（不是 D6 引入，建议单独决定）**：截图里按钮下方的大块空白是 `ios-browser` 的 80px 底部留白（D5 及更早就有）。这个 Safari 布局（地址栏在上、底部浮动工具栏不盖页面）下它是纯空白；其他工具栏布局是否需要，只能真机量。

## 2. 进度丢失（H1、H2）

**已排除（有测试证据）**：通关没写入（`renderFinish` 在结算页出现前就保存；结算页一出现就关浏览器、重开，关卡 / XP / 红心 / 连续天数 / 完成日期都在）；版本升级（`a1ecfd7` → `cfb368a` → `fcac0a5` → `f7c5f22` 存储键和格式 v3 不变，旧存档升级后原样保留）；Service Worker 更新（只删 `suipian-` 旧缓存，不碰 localStorage）；账号关闭分支；读不懂的记录（先备份再重置，并提示）；manifest / 跳转（`start_url`、`scope` 都是 `./`）。

**确认的缺陷：旧标签页回到前台会用旧进度覆盖新进度**
- `src/app.js` 约 1410 行：页面回到前台时 `regenHearts(state); persist()`，把本标签页内存里的整份旧状态写回；游客模式不监听其他标签页写入，`persist()` 写之前也不看存储里是否有更新的记录。
- 复现：标签页 1 停在地图 → 标签页 2 通关 U1L1（50 XP）并关闭 → 标签页 1 回前台 → 存储被写回 0 XP、0 关，之后新开也是空的（`tests/progress-persistence.test.mjs` C 组 4 项失败）。
- 来历：从 `a1ecfd7` 就有，**不是这次发布引入**。
- 与老大症状：如果 Safari 里还开着之前的碎片编程旧标签页，关掉刚通关的标签后回到旧标签，就会看到旧进度并把新进度覆盖。这是应用缺陷，不是操作失误；是否就是这条路，要靠核查 1 判断。

**可疑、本机无法判定**：①重开时进了预览入口（同域、不同存储键前缀，地址栏只显示域名，Safari 自动补全可能带到预览地址）；②无痕浏览（写入不报错，应用的无痕提示不出现，关标签即清空）；③Safari 个人资料或 App 内置浏览器（各自一份存储）；④没到结算页就关（只保存 XP、红心，关卡不算完成）——要问清“没了”是整份归零（又出开场介绍）还是只有那一关没完成；⑤读存储瞬时出错后空记录被存回（`app.js` 第 239 行，低概率，无备份）。

**平台限制（不是缺陷）**：iOS 上主屏幕 App 与 Safari 是两份独立存储，系统不搬；Safari 对 7 天未访问的网站会清脚本写入的存储（游客版长期风险）。

## 3. 存档风险

- 升级、Service Worker 更新、账号开关**都不删也不重置**存档。
- **旧标签页覆盖不可找回**（没有备份）。
- 如果只是 Safari 与主屏幕 App 分开、或进了预览入口，原进度**没被动过**，回原入口就能看到。
- 无痕模式：关标签即丢，找不回。

## 4. 修复方案（待产品官批准；未实现）

| # | 修复 | 改动 | 风险 |
|---|---|---|---|

| F4 | 读失败不存空记录 | `loadState` 读取抛错带标记，239 行遇标记不保存 | 低 |
