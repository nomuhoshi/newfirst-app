## 1. 先决问题

1. **主要用户在不在中国大陆？朋友打不开的那位在哪里？**
   - Firebase（Google）在中国大陆不能用，所以不选。
   - Supabase 从中国大陆能否稳定访问，**没有可靠结论**：官方没有中国区；社区讨论里有人说“不稳定”，也有人说“试了几分钟能用”，都只是个例。
   - GitHub Pages（github.io）在中国大陆的可用性同样没有验证过。
   - 如果主要用户在中国大陆，必须先请那里的朋友实测（建好项目后我会做一个测试页面），再决定是否投入。国内云服务（如腾讯云开发）一般需要实名认证和 ICP 备案，对住在日本的个人不现实。实测不通时的退路是“导出/导入进度码”（不需要服务器）。
2. **域名**：验证码登录需要自己的域名发信。暂不购买。购买前要：①检查项目主人是否已有可控制的域名；②核实首年价和续费价；③等访问实测通过、预算确认。
   - 方案 B（邮箱 + 密码）不发邮件、0 元，但忘记密码无法找回，**只留作内部测试用，不作为公开产品的登录方式**。

## 2. 登录方式

### 方案 A（推荐）：邮箱 + 6 位验证码
- 流程：输入邮箱 → 收到 6 位数字 → 在应用里输入 → 登录。新邮箱第一次登录就等于注册。
- 为什么不用“点邮件里的链接登录”：iPhone 主屏幕 App 和 Safari 的存储是分开的。点邮件里的链接会在 Safari 里打开，结果登录的是 Safari，主屏幕 App 里还是没登录。输入验证码就没有这个问题。
- 为什么不用密码：初学者容易忘密码，忘了还要做“找回密码”流程；没有密码也就没有密码泄露的问题。
- 需要：
  - Supabase 打开 Email OTP，验证码 6 位、10 分钟有效；
  - 邮件模板只写验证码；
  - 自定义发信（SMTP）。
- 发信限制：
  - Supabase 自带的发信每小时只有 2 封，只能发给项目团队成员，官方写明不能用于正式产品；
  - 改用自定义发信后，Supabase 默认每小时最多 30 封（可调）；
  - Resend 免费版每天 100 封、每月 3,000 封，**发件人必须是自己验证过的域名**，github.io 不能用，所以要买域名。
- 风险：QQ 邮箱、163 等国内邮箱的收信率没有验证过，上线前要实测。

### 方案 B：邮箱 + 密码（零费用）
- Supabase 关闭“邮箱确认”，注册登录都不发邮件。
- 代价：
  - 忘记密码无法找回；
  - 无法确认邮箱真的属于本人（别人可以用你的邮箱注册，但看不到你的任何数据）。
- 以后买了域名，可以在不换账号的情况下加上“验证码登录 / 找回密码”。

### 不选的方式
- 手机短信：要按条付费。
- 微信登录：需要企业资质。
- Google 登录：中国大陆不可用。
- Apple 登录：需要每年 99 美元的开发者账号。
- GitHub 登录：初学者大多没有 GitHub 账号。

## 4. 数据怎么存

### 4.1 本机
- 游客记录：仍是 `suipian.progress`（v3），**格式和版本号都不变**，现有的读取、迁移代码和测试照旧。
- 账号记录：每个账号一份本机副本，`suipian.acct.<用户编号>`。另有一条记录写着“当前是哪个账号”，以及本设备编号（随机生成，不含个人信息）。
- 登录凭证：由 Supabase 的工具包保存，退出时删除。

### 4.2 云端：一人一行
表 `progress`：`user_id`（主键，关联账号，删除账号时一起删）、`doc`（JSON）、`rev`（修改次数）、`updated_at`。

`doc` 的内容：

| 字段 | 内容 | 多台设备怎么合并 |
|---|---|---|
| `gen` | 第几代，从 1 开始 | 用户选择“用这份覆盖”时加 1；收到更高一代时，本机丢弃旧的账号副本（见 §5） |
| `xp` | `{ 设备编号: 这台设备挣到的 XP }` | 每台设备取较大值；**总 XP = 所有设备相加** |
| `runs` | `{ 设备编号: 这台设备完成关卡的次数 }` | 同上 |
| `done` | `{ 关卡编号: 第一次完成的时间 }` | 合并两边（取并集），时间取较早的 |
| `days` | 完成过关卡的日期列表 | 合并两边（取并集）。**保留全部学习日期，不截断**（数据量很小，每天一个日期字符串） |
| `hearts` | `{ 数量, 开始恢复的时间, 改动时间 }` | 以改动时间较晚的为准 |
| `prefs` | 音效、振动、按键音效 + 改动时间 | 以改动时间较晚的为准 |

- **为什么 XP 不会重复加**：每台设备只增加自己那一格，上传的是“我这台一共挣了多少”，不是“这次加了 10”。同一个数传两次，取较大值还是那个数；断网期间挣的 XP 在重连时只算一次。现有的 XP 规则不变（答对 +10、通关 +10、复习 +5），已知问题 #8（反复退出可以再刷 XP）也照旧。
- **连续天数不改规则，只改存法**：连续天数 = 从最后一个学习日往前数，连续有几天在 `days` 里。这和现在的规则（同一天只算一次、断一天重来）结果完全一样。旧游客记录只有“连续 N 天、最后一天 D”，迁移时换算成 D 往前 N 天的日期列表，结果不变。
- **红心（测试版：近似同步，有已知限制）**：
  - 规则：以**云端写入顺序**为准（后写入成功的那份覆盖前一份），**不单靠手机时间判断哪份更新**，因为两台设备的时钟可能不一致。恢复时间用“距离下一颗还差多少毫秒”加上云端记录的写入时刻来换算，设备时钟只用来算“过了多久”。
  - **限制（必须写进已知问题）：两台设备同时离线、各自扣了红心，联网后后一份会覆盖前一份，先到的那几次扣心会丢失。** 红心不会无限增加，但可能比实际多。之前写的“一两颗误差”没有依据，不再使用这个说法；误差上限取决于离线期间扣了多少次，最多是红心上限 5 颗。
  - 必须测试：同时扣心、扣心后恢复、两台设备时钟差几分钟甚至几小时、一台设备时钟在未来、断网期间恢复红心。
  - 红心只是展示和限制开始新关的机制，不影响已完成关卡和 XP，所以测试版接受这个近似；以后如果要精确，可以改成“按事件记录”。
- **不同步的项**：是否看过开场介绍、“添加到主屏幕”提示是否关掉。这两项按设备保存。

### 4.3 写入与并发
- 写入前先读云端的 `doc` 和 `rev`，在本机合并，再写回，条件是“`rev` 还是我读到的那个数”。
- 如果被另一台设备抢先写入，就重新读、重新合并、再写，最多 3 次。因为合并重复做也不会出错，重试是安全的。
- 合并规则写成不依赖界面的纯函数，用自动测试证明：先后顺序无关、重复合并结果不变。

## 5. 游客记录、首次登录、切换账号

**首次登录：**
- 本机游客没有进度 → 直接用云端进度（没有就新建）。
- 游客有进度、云端没有 → 询问“把这台设备上的进度保存到账号吗？”。选“保存”就上传；选“不保存”就先不上传，游客记录原样保留。
- 游客有进度、云端也有 → 显示两边的“已完成关卡数”和 XP，让用户选保留哪一份。**不把两边的 XP 相加。**
  - 选云端 → **游客记录保持不动，不会自动删除**，以后退出登录还能看到。
  - 选本机 → 用本机进度覆盖云端，`gen` 加 1。其他设备上那个账号的旧副本下次同步时会被替换；如果那台设备上还有没同步的进度，会显示“这个账号的进度已在别的设备上被替换”。
- **清空游客记录的条件（GPT 2026-11-03 批准，缺一不可）**：①用户明确选择了“转存到账号”；②上传成功；③**重新从云端读取，并确认内容与上传的一致**（完成的关卡、XP、学习日期、偏好都对得上）。三条都满足才清空；失败、超时、读回内容不一致，一律保留游客记录。
- 游客记录只导入一次：游客记录带一个随机“游客编号”，云端记下“已导入的游客编号”，重复触发（重试、两台设备）不会再导入。

**同一台设备换账号 / 退出登录：**
- 退出前，如果联网，先同步一次。
- 如果还有没同步的进度（断网），提示“还有未同步的进度，退出会丢失这部分”，可以取消。
- 退出后，删除这个账号在本机的副本和登录凭证，回到游客记录。**云端数据不删。**
- 下一个人登录时，读的是他自己的副本，看不到上一个账号的数据。

**删除账号：**
- 放在“我的”页，需要二次确认。
- 用一个数据库函数，只能删除自己的账号；进度表跟着账号一起删。
- 本机副本也一起删除。

## 6. 同步状态与离线

- 登录后，“我的”页和地图顶部显示：
  - 已同步（附时间）
  - 等待同步（断网或还没传完）
  - 同步失败（附原因和“重试”）
- 什么时候同步：
  - 每完成一关
  - 打开应用
  - 回到前台
  - 恢复网络
  - 短时间内多次触发只同步一次
- 断网时照常学习，只写本机副本，标记为“等待同步”。
- 登录本身需要联网；断网时登录按钮显示“需要联网”。
- Supabase 工具包按需加载：只有打开账号页或已经登录时才下载，第一次打开应用的速度不变；下载后也加入离线缓存。

## 7. 安全

- 网页里只放 Supabase 的“公开密钥”。这把密钥本来就会公开，配合数据库的行级权限，每个人只能读写 `user_id = 自己` 的那一行。
- 管理员密钥（service_role）**永远不放进网页和仓库**。
- 权限规则的 SQL 写进仓库（`supabase/schema.sql`），项目主人在后台粘贴执行。

### 7.1 XP 不重复计数：必须覆盖的测试
- 重复上传同一份：总 XP 不变。
- 第二台设备登录后下载到总 XP，**下载的总数不当作这台设备新挣的 XP**（本机 XP 格从 0 开始，只记录本机之后新挣的）。
- 第二台设备下载后再次上传：总 XP 不变。
- 游客记录首次迁移被重复触发（重试、两台设备同时）：只导入一次。
- 浏览器数据被清除后重新登录：设备编号丢失，会生成新的设备编号，新设备的 XP 格从 0 开始，**旧设备编号下的 XP 仍然保留在云端并计入总数**，总 XP 不增不减。
- 断网期间完成两关 → 恢复网络 → 重复上传 3 次：总 XP 只加一次。

## 8. 怎么验收（对应 GPT 的五个重点）

| 验收重点 | 自动测试（CI 里跑） | 真机 / 人工 |
|---|---|---|
| 两个人的账号互不影响 | 模拟两个账号轮流登录，本机副本和显示的进度互不串号 | 用两个真实账号，确认 A 读不到 B（行级权限） |
| iPhone、iPad 同一账号能恢复 | 合并函数测试：两台设备各自挣 XP、完成不同关卡后合并 | iPhone 学一关 → iPad 登录，看到进度 |
| 旧游客记录安全迁移 | v3 记录换算成账号记录（XP、已完成、连续天数一致）；上传失败时游客记录不被删 | 用现有设备上的真实进度登录一次 |
| 断网重连不重复加 XP | 断网完成两关 → 恢复网络 → 重复上传 3 次，总 XP 只加一次 | 飞行模式下做一关，再联网 |
| 退出后看不到上一账号 | 退出后本机没有该账号副本，界面显示游客进度 | 同一台手机换账号 |

- 自动测试会拦截发往 Supabase 的请求，换成假服务器，所以 CI 不需要真账号。
- 红心的限制（§4.2）要在已知问题里写明，并在测试里覆盖。
- 行级权限只能在真实项目上验证，作为人工验收项。

## 9.5 本机数据层：已实现的细节（2026-11-03，PR 见 GitHub）
代码：`src/account-data.js`（纯函数：格式、合并、转换）、`src/account-store.js`（按账号隔离的本机存储）、测试 `tests/step5.test.mjs`（纯 Node，不需要浏览器）。**本阶段没有接入应用**：`app.js` 和 `storage.js` 没有引用它们，现有游客流程、记录格式（v3）完全不变。
- 在原设计上加了两处，是为了堵住漏洞：
  1. **`lineage`（这一代的随机编号）**：“同一代”不够。两台设备各自选了“用本机覆盖云端”，会产生两份同代但互相独立的文档；合并它们会把两边的 XP 相加。现在编号不同就返回 `conflict`，不自动合并，交给用户选。
  2. **红心只存相对时间**（“还差多少毫秒恢复下一颗”），不存设备时间戳。这样两台设备时钟差几小时甚至几十天，恢复出的红心和恢复进度都一样。代价：文档在云端停留的时间不补算（红心恢复偏保守）；接入云端后可以用服务器时间补算。
- 红心谁说了算：不比较时间，用同步层传入的 `localHeartsDirty`（自上次同步后本机是否扣过 / 恢复过红心）：改过 = 本机这次写入排在云端当前内容之后，用本机的；没改过用云端的。设置同理（`localPrefsDirty`）。
- 已验证的限制：A 扣 1 颗、B 扣 2 颗，都在离线时发生。谁后写入，谁的结果留下；最多比实际多 5 颗（红心上限），不会无限增加。
- 游客记录转换：XP 和完成次数记在“导入它的设备”名下；连续 N 天换算成最后一天往前的 N 个日期；原游客记录一个字节都不改。只有 `clearGuestAfterVerified` 一处会删游客记录，必须同时满足三个条件。
- 还没做（都在后面的步骤里）：登录、云端读写、同步层（版本号冲突重试、同步状态显示）、首次登录的选择界面、切换账号界面、删除账号、隐私说明。
