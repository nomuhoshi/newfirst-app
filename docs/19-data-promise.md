# 数据承诺：用户的学习数据，改版不丢

写于 2026-11-04（程序员 Sonnet）。**任何改动存储、同步、关卡编号的人（和 AI）开工前先读完这一页。**
目标一句话：**朋友注册之后，不管以后怎么更新迭代，他的 XP、已完成关卡、连续天数都在。**

## 1. 数据现在存在哪三层

| 层 | 在哪 | 格式 | 谁写 |
|---|---|---|---|
| 本机记录（游客） | 浏览器 localStorage，键 `suipian.progress` | 第 3 版（`DATA_VERSION = 3`，`src/storage.js`） | 这台设备 |
| 账号的本机副本 | localStorage，按账号分开（`src/account-store.js`） | 账号文档 | 这台设备 |
| 云端 | Supabase 表里的 `progress.doc` | schema 1（`SCHEMA = 1`，`src/account-data.js`） | 用户自己的设备 |

合并规则（不能改）：**每台设备一格 XP，合并时每格取较大值再相加；完成关卡取并集。** 改成直接相加会重复计分，改成后写覆盖会丢分。

## 2. 改版铁律

1. **关卡编号只能追加。** 不改名、不删除、不挪到别的单元、不复用旧编号。用户的完成记录就是按编号存的（`done` 的键），改了编号 = 作废他们的进度。
   - 关卡正式上线时，把编号追加到 `tests/fixtures/released-lessons.json`。
   - 要下线一关，是“隐藏”，不是删除。
2. **本机格式升级（`DATA_VERSION`）必须带迁移。** 写一个函数把旧版转成新版、进度原样带过去，并把旧版的真实样本放进 `tests/fixtures/`。**绝不允许“格式无法识别 → 从头开始”这条路对线上用户发生。**
3. **云端文档新增任何字段，必须同时升 `SCHEMA`。** 现在的 `normalizeDoc` 会丢掉不认识的字段；老客户端读到更高的 schema 会拒绝处理（这是对的），但读到同 schema 的新字段会把它抹掉再写回去。新版客户端必须能读所有旧 schema。
4. **格式变更分两步发布（先能读、后能写）。** 第一步只发“能读新格式”的版本；等大家都更新（Service Worker 缓存会让部分设备慢几天）以后，第二步才发“开始写新格式”的版本。否则回滚或者缓存里的老版本会碰到读不懂的数据。
5. **`tests/data-compat.test.mjs` 的预期值不能为了让改动通过而改。** 它红了说明你在动用户的数据：改代码适配样本，不要改样本适配代码。样本的格式是已经存在于用户手机和云端里的真实格式。

## 3. 这次新增的保护（分支 `sonnet/data-keep-forever`）

- **读不懂的本机记录先备份再重置**（`storage.js`）。之前：记录损坏或版本不认识 → 提示“已从头开始” → `app.js` 立刻把空记录存回去 → 原进度永远没了。现在：重置前把原始内容原样留一份（最多 3 份，键 `suipian.progress.unreadable.<时间戳>`）。用户自己点“清除学习记录”不备份，那是他的决定。
- **30 项样本测试**（`tests/data-compat.test.mjs`，已加进 `npm test`）：本机 v3 样本、云端 schema 1 样本、合并幂等与不丢分、拒绝更新版本的文档、已上线关卡编号锁。
- 验证方法：故意拆掉备份 / 把 `DATA_VERSION` 升到 4 / 往已上线清单放不存在的编号 / 让云端校验不再拒绝新版本，各自都会让对应的测试变红（5、7、1、2 项）。复原后 30/30。

**这些保护的边界**：备份存在 localStorage 里，用户清除网站数据、或 Safari 长时间不用清理（`docs/14` 第 7 条）时会和主记录一起没。目前**没有界面入口**把备份找回来，只有 `listUnreadable()` 接口，需要人工或以后做“找回”页面。

## 4. 还没覆盖的风险（诚实清单）

| 风险 | 现状 |
|---|---|
| **Supabase 免费版闲置 1 周会被暂停** | 官方定价页：“Free projects are paused after 1 week of inactivity.” 暂停期间朋友登录、同步都不可用（本机数据还在）。暂停不等于删除，能一键恢复（来自第三方文章，没有看到官方承诺的恢复期限）。 |
| **免费版没有自动备份** | 官方定价页：Free 的 automatic backups 为 Not included。数据库被误操作或损坏，云端数据就没了。 |
| 付费才有备份 | Pro 从 $25/月起，每日备份保留 7 天；时间点恢复（PITR）是额外 $100/月（7 天保留）。 |
| 防暂停的定时访问算不算“活动” | **未验证。** 不要当成已解决。 |
| 云端被清空后，设备上的本机副本会不会重新上传 | **未验证。** 要用假服务器测一遍再下结论。 |
| 没有“导出 / 导入进度文件” | 用户清了浏览器数据又连不上云端时，无法自救。 |
| 没登录的用户 | 只有本机一份，Safari 约 7 天不用可能被清（`docs/14` 第 7 条）。云端保障只对已登录的人成立，所以“什么时候引导注册”很重要。 |
| 账号找回 | 登录是邮箱验证码。丢了邮箱怎么办，没有设计。 |
| 老大的 Supabase 账号本身 | 账号被盗或误删项目 = 所有人的数据一起没。需要二次验证、定期导出。 |

## 5. 需要老大决定

1. **朋友开始用之前，要不要升 Supabase Pro（$25/月起）？** 这是花钱，我不会自己决定。不升的话，至少要有第 2 条。
2. **不花钱的下一步做哪个？** 我的建议顺序：①“导出 / 导入进度文件”（0 成本，直接保护用户）；②定期把云端数据导出到你自己能保管的地方；③防暂停的定时访问（先验证是否有效）。
3. **同步层改动合并前，建议切 Opus 复核**（TEAM.md 规则：同步、数据库安全归 Opus）。
